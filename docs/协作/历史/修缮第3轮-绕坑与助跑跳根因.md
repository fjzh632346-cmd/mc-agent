## 一句话结论

她从坑里爬出来之后，回家的路不再从坑口上面跳过去了——现在会贴着坑边绕开走，十次全对，一次都没再掉下去。

## 白话摘要

先把毛病看清楚了。上一轮说她"爬出来又掉回坑里"，我原以为是找路时看不出那是个坑，实测发现真相更具体：她站在自己垒的柱子上往家走时，会**助跑起跳、直接从坑口上方飞过去**。跳过去了就没事，一次没跳好就摔回坑底，重新自救——来回折腾正是这么来的。逐帧记录抓到了这一跳：起跳、腾空、落地，整个过程一秒出头。

改法是给她加了一本"哪些地方困过我"的随身记性。被困过、而且真的靠脱困梯子折腾出来的地方，会被记下来；之后找路时，那个坑的口子连同上方的空中一并当成不能走的地方，于是她不再有"从上面跳过去"这个选项，只能老老实实沿着坑沿绕。真机上从同一个位置试了十次，十次都是往旁边挪一步踩到实地、再贴边绕过去，全程贴着地面走，没有一次起跳，没有一次掉下去。绕完照样走回了家（一百三十米的路，到家了）。

有一件事要专门说：第一版做完真机一跑就出了新毛病——她在回家路上一处普通的斜坡卡了一下，那块**平地也被记成了坑**，还是一大片，结果回家的路被自己划的禁区挡住了。这正是任务书提醒的"别把所有洼地一刀切"。我当场改了判定：现在不看她怎么出来的，改成**量地形**——从坑底往上一层层试，只要这个"坑"还是封闭的就继续往上，一旦漫到周围的平地就说明上一层才是坑沿。斜坡一试就漫开，所以不算坑。改完再跑，一百三十米的路上一个误记都没有，也没再挡过路。

另外还加了一道保险：万一因为绕坑真的找不到路、而且她原地没动过，会自动放弃绕行、按原来的走法再试一次。宁可走危险的路，也不能把她困在原地。

顺带把第 1 轮遗留的一个疑问查清了：她的施工记录里**确实写进了世界名字**。四十九条真实记录里，八月一号之后开工的都带着世界名字，七月底之前的都没有——正好卡在启用专用服务器那天，说明这个机制是从那天起真的生效了，不是没写。

### 一、复现与根因（已证实）

复现场在修缮线自己的世界（25566），**全程没碰建造线的服务器和世界**。
先核实现场几何（RCON 逐格探测）：

```

四周   地面实体面 y=64（脚下站位 y=65）→ 正好四格深
```

**先复跑上一轮的全程**（`.tmp/bot-r3b/r3c/r3fix*.out.log`）：
`repath → jump_and_step(无位移) → nearby_exit → safe_dig(no_safe_block_to_dig) → pillar_up`
的升级顺序与第 2 轮同形，**已证实**。

**根因不是"寻路把坑当成可走地面"**（**已证实，与我最初的猜测相反**）。
纯净基线：把她放在坑东侧 (564.5,65,375.5) 让她回家，她**主动绕过整个坑**从南侧走了，
没有掉下去——A\* 本来就不会规划一条"跳下去出不来"的路。

**真正的根因是助跑跳**：把她放在爬出后所在的位置（自己垒的柱子顶 558.5,65,376.5）再让她回家，
100ms 逐帧轨迹（`.tmp/watch-pos.js`，RCON `data get entity LinXia Pos`）：

```
+5.1s 558.50,65.75,377.03   ← 起跳
+5.2s 558.50,66.25,377.68   ← 腾空最高点
+5.3s 558.44,65.12,379.10   ← 落到坑南岸（z=378 起是实体）
```

x 不变、z 从 376.5 直接到 379.1、y 拱到 66.25 —— 这是一次**跨越坑口的冲刺跳**，
不是绕行。`mineflayer-pathfinder` 2.4.5 的 `getMoveParkourForward` 在 `allowSprinting`
下最远跳 4 格，坑口宽度在这个范围内，代价只有 1。跳成了无事，跳失手就回到坑底——
第 2 轮 10:14:53 那次就是失手的一次。**这一跳我复现了 5 次，5 次都跳成功**，
说明它是概率性失手，不是必然，这也解释了为什么第 2 轮只观察到一次。

### 二、为什么不能用代价模型解决（已证实）

`movements.exclusionAreasStep` 只在**落点**上被查询：

- `getMoveForward` → `exclusionStep(blockC)`（目的地脚下格）
- `getMoveDropDown` → `safeOrBreak(blockB/C/D)`（目的地一列）
- `getMoveParkourForward` → `cost += this.exclusionStep(blockB)`，**blockB 是落点的头部格**

助跑跳的落点是坑对岸的正经地面，**飞越的那个洞从头到尾没有进过任何一次代价计算**。
所以把坑标成"贵"没有用，必须改变规划器对那些格子的**认知**。

### 三、改法

**新增 `systems/terrain-hazards.js`** —— 进程内的"困过我的地形"台账 + 寻路接线。

判定一个地方值不值得记，两条**互相独立**的门槛都要过：

1. **脱困台账证据**：`ledger.exhausted.length >= hazardMinFailedRungs`（默认 2）。
   一级失败是打嗝，不是危险地形。
2. **地形本身量得出是个封闭的坑**（`measureHole`）：
   从坑底往上逐格抬高候选坑沿 h，每一层做一次列泛洪
   （"地面高度 < h 且能从锚点连通的列"）；只要泛洪**自行收敛**就说明还是个坑，
   一旦漫到半径/列数上限就说明这一层已经溢到周围平地了 —— **最后一个收敛的 h 就是坑沿**。

坑沿 = 洞内最高一格。危险区 = 泛洪出来的那些列 × `[坑底, 坑沿 + 2]`。
上面那 2 格净空是关键：助跑跳的飞行轨迹就在坑沿上方一两格，
不把它算进去，跳这条路依然是免费的。

**接线在 `actions/move.js`**：`avoidKnownTerrainHazards()` 包一层 `movements.getBlock`，
把危险区内的格子标成 `safe = false` —— 和本文件里既有的 `enableDoorTraversal`
重分类门方块是同一套手法，不动寻路库本体。效果：

| 走法 | 结果 |
|---|---|
| 走进坑口 | `safeOrBreak` 对空气返回 100 → 代价 >100 → 该走法被丢弃 |
| 从坑沿掉下去（`maxDropDown=4`） | 同上（blockD 在危险区内） |
| **跨坑口助跑跳** | `getMoveParkourForward` 首行 `!getBlock(node,dir.x,0,dir.z).safe` → 直接 return，该方向不再产生跳跃 |
| 沿坑沿走（坑外实体地面） | **完全不受影响**——那些列的地面高度等于坑沿，压根不在泛洪结果里 |

**三条让路规则**（这是"不误伤"的主体）：

- **她正待在坑里 → 该坑整体不生效**。否则脱困梯子自己的 `moveTo` 会一步都走不了。
  判据用坑沿而不是净空顶：她站在自己柱子顶上是 `坑沿+1`，那是**站在上面**不是"在坑里"，
  这条边界搞错了避让就恰好在最需要的时刻失效（写这条时踩过，已钉单测）
- **目的地在坑里（或紧邻）→ 该坑整体不生效**。挖矿、进工地基坑干活本来就该走到洞底
- **`avoidKnownHazards: false`** 显式关闭

**兜底 `shouldRetryWithoutHazards`**：绕坑绝不能把"到得了"变成"到不了"。
`moveTo` 失败时，若（a）确有记住的坑落在起点—终点走廊内、且（b）她**原地没动过**，
就关掉避让重规划一次。加 (b) 是因为在这里"长途走到超时"是常态，
每趟长途都赔一个完整超时会是新的退步。

**生命周期**（任务书要求写明）：

| 项 | 设定 | 理由 |
|---|---|---|
| 存放 | blackboard `recovery.terrainHazards` | **进程内**，重启即忘：重启后世界可能已变，抱着过期禁区更糟 |
| 过期 | 15 分钟，同一地点再困一次就刷新 | 覆盖一次撤退 + 随后的回家路 |
| 坑被填掉 | 每次读取时抽查（最多 12 列、每 5 秒一次）；**全部填到坑沿即删除** | 直接回答"填掉后不应永远绕着走" |
| 上限 | 8 个地点，最旧的先淘汰 | 世界不会慢慢变成雷区 |
| 泛洪上限 | 半径 6、121 列 | 一个坑，不是一条峡谷 |
