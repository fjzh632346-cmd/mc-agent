### 二、本轮要回答的问题①：pathfinder 有没有便宜的路径代价接口？

**有，而且天然就是有界的。已证实。**

```text
node_modules/mineflayer-pathfinder/index.js:63-68   getPathTo(movements, goal, timeout)
node_modules/mineflayer-pathfinder/index.js:70-101  getPathFromTo(...) 生成器
node_modules/mineflayer-pathfinder/lib/astar.js:55-58  makeResult() → { status, cost: node.g, path, ... }
```

关键点：`getPathTo` 内部只取生成器的**第一个切片**（`generator.next()`），而 A* 的单切片同时受 `timeout` 和 `tickTimeout`（默认 40ms）双重约束。所以它**最多跑 min(timeout, tickTimeout) 就返回**，并给出 `status`（`success` / `partial` / `timeout` / `noPath`）和 `cost`。这正是需要的"便宜的估算"，不需要跑完整寻路。

一个必须注意的语义（已在代码注释里写明）：`partial` / `timeout` 状态下的 `cost` 是"当前最优节点的 g 值"，**不同候选之间不可比**。所以我只在 `success` 档内用 `cost` 排序，其余档位一律退回原始顺序。

顺带确认：项目里已有一套同类机制（`actions/build.js:5764-5800` 的 `previewControlledVerticalAccessPath`），但只服务于"受控垂直通道"这一条窄路径，普通站位选择用不上。本轮没有复用它，因为它的切片预算是按垂直通道的选项算的；两者共用会互相污染配置。

### 三、本轮要回答的问题②：B-11 会自动缓解吗？

**部分缓解，但不会自动消失。合理推断。**

B-11 的机制是 `systems/building-system.js:6313-6317` 的 `shouldPreferOutsideReservedBounds()` 在非内饰阶段一律返回 true，导致 `actions/build.js:5959-5963` 把屋内站位排到最后。

本轮的预筛跑在**更靠后**的位置（`moveToFirstReachablePlacementStand` 入口），排序键的优先级高于原有的全部键。因此封闭房屋里那种"屋外站位在直线上更近但寻路走不通"的情形，现在会被 `noPath` 降到第 2 档，屋内站位自然上浮——**这一类会被自动救回**。

但有一种情形救不回：屋外站位**寻路上确实走得通**（门已装好、门感知寻路已生效），只是路线绕远。这时两个候选都是 `success` 档，改由路径代价排序——绕远的屋外站位代价更高，仍然会被排到后面。所以实际覆盖面比我最初估计的更大。

**唯一确定救不回的**：屋外站位路径代价更低但从那里根本够不着目标。那属于 reach 判定，不属于本轮范围。

结论：B-11 大概率被显著缓解，但**没有真机证据**，不建议就此关闭该条目。建议等真机验收跑通后，用一次封闭房屋的内部清理来单独确认。
