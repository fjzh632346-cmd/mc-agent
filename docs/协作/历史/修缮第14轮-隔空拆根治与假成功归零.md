## 白话摘要

先说清楚一件事：上一轮我记的「起的程序会自己消失」是误判，建造 20 收工时按名字关进程把我的连着一起关了，已经从我的池子和记忆里划掉。

这一轮的病是「隔空拆」。她要拆自己垫的临时脚手架时，不管那根柱子离她多远，都会直接发一个「开挖」的请求；用的那个挖矿库有个习惯：发完请求以后不等服务器回话，自己按挖土需要的时间掐个表，时间一到就把自己脑子里那块土改成空气。我们的确认逻辑只看她脑子里那份地图，看到空气、稳定三百五十毫秒，就写下一行「拆掉了」。服务器那边呢？超出手臂长度的请求它直接不办，也不发纠正——所以她脑子里那格永远是空气，日志永远说成功，地上那根柱子一直立着。这就是建造线现在得拿命令一格一格去清的三十一格土的来路。

我把这条在自己的服务器上原样重放：让她站在十四格外去挖一块土，挖矿的接口一点二秒后返回「成功」，六秒后她脑子里那格还是空气，地上没掉出土块，服务器发回来的只有一句「收到你的动作」、没有任何方块更新，用命令查那格还是土。同一块土从三格外挖，服务器立刻回了方块更新、掉了土块、真的没了。所以判据很清楚：够得着就是真的，够不着就是假的。

又把建造 20 那份日志按这个判据从头算了一遍——每次「拆掉了」的时候她站在哪、有没有掉出土块（真挖掉一定掉东西）：四点五格以内一百三十三次里一百三十次是真的，八格以外十三次没有一次是真的。

改法分两层。第一层诚实：挖之前先按挖矿库自己的那把尺子量一下，够不着就不发请求、写一行「这格够不着，距离多少」，并把这格记进一本账；而且这格以后再看到「是空气」也不认——因为那正是被骗的那份地图，建造 18 和 20 就是这样对同一格反复「拆」了五次。第二层提高成功率：够不着不等于办不到，先走过去（路上不许垫方块也不许挖），到了再挖；走不过去，就回到第一层老实认账。留下的格子只记账不算失败——否则刚盖上的那块砖会跟着整步一起黄掉。

真机同一根柱子、同一个起点，改前：六条「拆掉了」，服务器上六块土一块没少，她一步没动；改后：她走过去，六块全部真的没了，服务器上一块不剩。把走路那条关掉再跑，就是第一层的样子：零条假成功、六条「够不着」、账上六格、她脑子里那格也如实还是土。另外从零盖一整栋小屋一百八十四步照样一次成，新逻辑一次都没被触发；盖一整座十一格高的靶塔，二十八次拆全是真的，事后逐格查二十一格脚手架，一格残留都没有。

顺带修了一条：日志里那句「垫了一块脚手架」其实是拿她脑子里的地图变化认的——而服务器把被假拆的方块放回来时，看起来正好也是「空气变成土」。所以建造 20 出现过「人在十四格外却说自己垫了一块」。现在超出手臂长度的变化不再算作她垫的。

第三步（任务失败就往家跑）取证做完了：失败那一刻她离工地锚点只有 2.22 格，而工地半径是 64 格——本该判「就在工地上、别走」。真正的原因是那个锚点在十五分钟前就过期了（保鲜期三分钟）。为什么盖房的十五分钟里锚点一次都没被刷新，日志里看不出来，我没有硬猜，按任务书交回去当设计题。

### 二、第 1 步：取证

**2.1 挖掘流程：假成功是怎么来的（已证实，读码 + 真机探针）**

`node_modules/mineflayer/lib/plugins/digging.js`：

- `dig()`（`:18`）**不做任何距离检查**，直接 `bot._client.write('block_dig', {status:0,…})`（`:130`），然后 `setTimeout(finishDigging, bot.digTime(block))`；
- `finishDigging()`（`:143`）发 `status:2`，随即 **`bot._updateBlockState(block.position, 0)`（`:158`）——把方块在客户端世界里改成空气**；
- 这一步会触发 `blockUpdate:${pos}`，而 `onBlockUpdate`（`:192`）正是 `dig()` 等待的那个事件（`newBlock.type === 0` → `diggingTask.finish()`）。**所以 `await bot.dig()` 的 resolve 完全由客户端自己的定时器产生，链条上没有任何一处问过服务器。**
- 库里唯一那把尺子是 `canDigBlock`（`:220-226`）：`block.diggable && 方块中心到眼睛(pos+1.65) ≤ 5.1`。**我们的代码从来没调用它。**

真机探针（修缮世界 25566，`.tmp/r14/dig-probe.js` / `dig-probe2.js`，同一次连线内两次对照）：

| | 近（3.21 格，`canDigBlock=true`） | 远（14.05 格，`canDigBlock=false`） |
|---|---|---|
| `bot.dig()` | resolve，819 ms | **resolve，771 ms（一模一样）** |
| 客户端该格 | air | air |
| 服务器发回的包 | `acknowledge_player_digging{sequenceId:0}` + **`block_change{location:663,100,275,type:0}`** | 只有 `acknowledge_player_digging{sequenceId:0}`，**没有任何 block_change** |
| 掉落物 | 有（item 实体 2→3） | **没有**（3→3） |
| RCON 实况 | air | **仍是 dirt** |
| 之后 +0.5/1/3/6 s | — | 客户端**一直**是 air（自己永远不会纠正） |
| 走到它旁边（1.52 格） | — | 客户端仍是 air |
| 跑远再回来（区块重载） | — | **客户端恢复成 dirt** |

结论（**已证实**）：服务器对超距挖掘的反应是「回一个 sequenceId=0 的 ack，不发方块更新、不改世界」；mineflayer 不实现方块预测回滚（全仓没有 `acknowledge_player_digging` 的处理），且 `block_dig` 一直发 `sequence` 缺省值，所以那个 ack 什么也纠正不了。**客户端世界从此长期与服务器不一致，直到区块重载。**

**2.2 我们自己那三个函数（已证实，读码）**

- `clearTemporaryPlacementReference`（`actions/build.js:3718`）：只按 `positions` 倒序逐格调用下一个函数，**不走位**。看不出「当初默认她就在旁边」以外的设计意图：同文件里放置那一侧有 `ensureTemporaryReferencePlacementReach`（`:3691`）专门负责「够不着就挪过去」，拆这一侧没有对应物——**是漏了，不是有意为之**。
- `clearTemporaryReferenceBlock`（`:3790`）：`bot.blockAt` 取块 → 保护区检查 → **`await bot.dig(block)`，无距离判据**。
- `confirmTemporaryReferenceClear`（`:3858`）：只轮询 `bot.blockAt`，连续 `temporaryReferenceClearStableMs`（默认 **350**）读到空气即成功。这个 350 ms 的来路：全仓只有这一处用它，没有注释也没有对应的单测说明，**UNKNOWN**；从量级看它挡的是「放置/破坏后一两个 tick 的抖动」，挡不了本轮这种「客户端被永久改脏」。
- 对照：放置那一侧 `placeTemporaryReferenceBlock`（`:3752`）用的是 `confirmPlacedBlock(..., { requireServerConfirmation: true })`。而且 mineflayer 的 `placeBlock`（`place_block.js:13`）**会等一个真的服务器 blockUpdate**（5 s 超时，等不到就抛 `No block has been placed`）。**放置是服务器确认的，拆除不是——这个不对称就是本轮的病灶。**
- `BUILD_VERTICAL_ACCESS_CLEANUP`（`:1087`）、`BUILD_VERTICAL_ACCESS_CANDIDATE_CLEANUP`（`:7248`）、`recoverUnreservedTemporaryCornerResidue`（`:7063`）**都走同一个 `clearTemporaryReferenceBlock`**，所以三条路一起中招、也一起被这轮的补丁覆盖。

**2.3 那 56 格为什么成功了：距离 vs 真拆掉那条线（已证实）**

脚本 `.tmp/r14/clear-distance.js` / `clear-replace.js`。做法：把每条 `[BUILD_STAIR_TEMP_REFERENCE_CLEAR]` 和最近的 `[状态]` 位置配对算距离，再用一个**与位置无关的第二判据**交叉验证——`[pickup-detect] itemPos=…`，**真的破坏一定掉土块**。

先把两处伪残留剔掉：

- `600,67..74,-8` 这 8 格是**脱困柱**放回去的：`[ESCAPE_PILLAR] pos=600,67,-8 … result=placed` 等 12 行出现在它们最后一次被清之后（02:14:31–53，`STUCK_DETECTED in_hole` 触发）。**它们不是没拆掉，是拆掉后又被垫了一次**——建造 20 的残留名单把这批和「3 根逃生柱」重复计了。
- `601,69..73,-10`（5 格）与 `608,71,-8`：清的同时有 `[pickup-detect] itemPos=601,73,-10 / 602,71,-9 / 601,69,-10` 等掉落物，**服务器确实破坏了**。它们为什么在建造 20 的 RCON 扫描里仍是 dirt，我这边解释不了 → **UNKNOWN**（建议建造线复核那次扫描的时点与坐标）。

剔除后，逐条 CLEAR 的表（184 条）：

| 那一刻的距离 | CLEAR 条数 | 掉了土块（= 服务器真拆了） |
|---|---|---|
| ≤ 4.5 | 133 | **130（98%）** |
| 4.5 – 5.1（`canDigBlock` 仍为真） | 6 | 6（100%） |

**2.4 `SCAFFOLD_PLACED` 的时机（已证实）**

它不是在发包前也不是在收到确认后打的：`actions/move.js:562 trackMovementScaffoldPlacements` 监听**客户端 `blockUpdate` 事件**，条件是「旧的是空气、新的是脚手架材料」。因为 mineflayer 的**放置**必须等服务器的 blockUpdate（`place_block.js:13`），所以**正常的 `SCAFFOLD_PLACED` 是服务器背书的**。

那么 01:35:28 那条 `position=598,69,-18` 而人在 `607.5,67,1.3`（14 格外）是什么？**是服务器把被假拆的方块放回来的那一下**——探针已证实「跑远再回来，客户端那格恢复成 dirt」，那正是一次 air→dirt 的 blockUpdate，与「她垫了一块」在这段代码眼里长得一模一样。同一格 `598,69,-18` 在建造 20 日志里「放置→清除」重复了 5 轮（P25:10 C25:54 / P27:11 C27:59 / P35:28 C36:17 / P42:25 C43:35 / P00:15 C00:59），全程服务器上一直是 dirt。**合理推断**（机制已证实，这一条具体日志行的因果未单独复现）。
