## 白话摘要

这一轮不修某个单独的毛病，而是第一次把她当成一个真人陪玩来验：从「跟着我」开始，一路走到记基地、去挖矿、叫停、继续、合成、烧炼、记箱子、存东西、取东西、盖房子、照看农田、天黑、刷怪、回家，中间故意在她干活干到一半时插话、插事、改天色、放怪，专门看几件事撞在一起时会怎样。一局跑下来，十六条问题浮出来，其中三条会直接挡住「基础可玩」。

最狠的那条是这样的：她心里有两把尺子。一把管「什么事更要紧」，按这把尺子，保护你比盖房子要紧；另一把管「谁先排的队」，按这把尺子，盖房子排在保护前面。平时两把尺子给的答案一样，看不出问题；一旦不一样，就会出现她放下砖头准备去保护你、下一瞬间又觉得应该接着盖房、于是又放下、又捡起来——真机上八十秒里来回了三十八次，砖也没砌几块，保护你的事一次都没真的开始。改法是让两处都用同一把尺子，就是一行判断。改完在同一个场景再跑一遍：一次就交接过去了，保护做完，房子自己接着盖到完工。

另外两条挡路的：一是**她死了整套系统不知道**。真机里她被僵尸逼到平台边上摔下去死了一次，在一千一百格外的出生点复活，而她自己和所有系统都没意识到发生过死亡，只是发现「我离基地好远」，然后开始往回走，走进坑里出不来，最后喊人来拉。二是**你站在她要盖房的地方，她会直接失败**，而且只回一句「这一步没处理完整」——不会告诉你往旁边挪一步就行。她刚刚还在跟着你走呢，你说「在这儿盖个房」，她就卡在这儿了。

还有几条属于「一件事做不完另一件事」：背包一满，她就每三十秒自己往家跑一趟，把你刚下的命令顶掉，而回到家背包还是满的，于是循环；让她烧铁，她说没燃料，可她三分钟前刚亲手把三十二块煤放进那个她记住的箱子里，箱子就在三格外——盖房子缺料会回箱子取，烧炼不会；你让她「去挖矿」，她挖的是脚底下那块石头，把自己摔了半管血，而盖房子那边早就有「别挖自己站的地方」这道闸，采矿这边没有。

看板上原来存疑的两条也验完了：一条属实，就是上面那把尺子的问题；另一条是虚惊——她夜里根本不会自己去睡觉，这个动作是空的，所以谈不上抢先。

## 需要老板拍板的问题

### 问题 1：「基础可玩版」先修哪三条？

- 背景：这局抓到十六条，全修要好几轮。我按「多挡玩」排了序，头三条挡得最狠（第二至第四条，第一条我这轮已经修掉了）。
- 选项 A：**按我排的顺序来**——先做「她死了没人管」，再做「你挡在工地上她只会失败」，再做「背包满了反复空跑」。代价：三条各一轮，两条要动生存与建造的交界，第一条要新加一段死亡处理。
- 选项 B：**先做便宜的**——「说给玩家的话对不上真实原因」这条只有两句写死的话在管所有失败，改成一张对照表，一轮能把十几种失败一次说清楚。代价：不解决任何行为问题，只是让她说人话；但玩家的挫败感会立刻下降一大截。
- 我的建议：**A，但把 B 顺手捎上**。因为 A 的三条都是「她真的做错事」，B 只是「她没把做错的事说清楚」；不过 B 的改动小到可以塞进 A 的任何一轮里做完。

### 问题 2：「连玩一局」这套流程下一轮怎么走？

- 背景：这次的序列覆盖了十八种活里的十种。没验到的八种是：捡东西、找路探索、穿盔甲、备战、睡觉、打单个怪、挖指定方块、回到玩家身边。
- 选项 A：**下一轮补齐剩下八种**，把序列扩成完整一局。代价：一局的真机时间会从四十分钟涨到一小时以上。
- 选项 B：**下一轮不扩，改成把这轮抓到的头几条修掉**，序列原样复跑当回归。代价：没验的八种里可能还藏着更狠的。
- 我的建议：**B**。这轮已经攒了十六条，先还债；序列当回归跑一遍成本很低（脚本可复跑）。补齐八种排到再下一轮。

### 四、第 3 步：最狠那条的根因与改法

**根因（已证实）**：`TaskManager` 里有两把尺子。

- `maybePreempt`（`tasks/task-manager.js:222`）问的是 `taskArbiter.resolveConflict` → 走 `TaskPriorityManager` 的**仲裁档位**（保命/优先/常规/闲时）。`guard_player` 在 `COMBAT_TASKS` 里 = **CRITICAL(10)**，`build_blueprint` 在 `MEDIUM_TASKS` 里 = **MEDIUM(5)** → `critical_preempt` → 施工挂起、`currentTask = null`。
- `startNext` 紧接着调 `selectNextTask`（`:293`），那里比的是 `queued.priority > paused.priority`，也就是 `ai/intent-to-task.js` 里写死的**入队序号**：`guard_player` 是 **8**（`:75`），玩家施工令是 **11**（`PLAYER_BUILD_PRIORITY`，`:12`）。`8 > 11` 为假 → 走 `if (paused) return removePausedTask(...)` → **把刚挂起的施工又拿回来当当前任务**。

下一 tick 重来一遍。两处永远给相反答案，于是每 tick 一次挂起、一次恢复，队列里那条 CRITICAL **永远排在队头、永远轮不到**。

**离线复现（`.tmp/r16/repro-thrash.js`，改前）**：

```
tick 0  current=build_blueprint#1  queue=[guard_player]  paused=[]
...
tick 7  current=build_blueprint#1  queue=[guard_player]  paused=[]

preempts in 8 ticks: 8
guard ever became current: false
```

**改法（一行判断，`0f1a4fb8`）**：`selectNextTask` 改用仲裁器自己的比较器——

```js
if (queued && (!paused || this.taskArbiter.compareTasks(queued, paused) < 0)) {
```

`compareTasks` 就是 `sortQueue` 排队列用的那一个（档位降序 → `createdAt` → `id`）。改完之后**队列内部的排序、抢占的判断、队列与挂起栈之间的挑选，三处用的是同一把尺子**，结构上不可能再互相拆台：若挂起的那条档位不低，它被接回来之后 `resolveConflict` 会判 `incoming_priority_not_higher` → QUEUE，不会再抢。

**离线复现（改后）**：

```

tick 1..7 同上（不再变化）

preempts in 8 ticks: 1
guard ever became current: true
```

### 五、两条看板疑点的结论 + 第 15 轮回归
