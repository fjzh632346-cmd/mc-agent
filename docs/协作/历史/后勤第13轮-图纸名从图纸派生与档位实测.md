## 白话摘要

先说一句得罪人的实话：任务书里写的前提（「只有四个名字点得到」）**不对**。我逐句实测下来，她认得的名字其实不少。真正的毛病是另外两个，而且都比「点不到」更难发现：

**第一个：说了她不认识的名字，她不会问，会默默盖成小房子。** 「建个雕像」「建个喷泉」「建个临时避难所」这三句，以前都被当成「小房子」，她二话不说去盖房子。只有一份图纸是真的完全点不到（双层小木屋），怎么说都会被听成另一份。

**第二个（这个更隐蔽）：名字叫对了，也可能什么都盖不出来。** 她给「随口一说」的建造统一按「简单小屋」那档算账，而那档要求**至少一百二十块**。雕像才十六块、喷泉三十一块、避难所五十四块——名字明明说对了，还是会被这道门槛挡回来，结果是一块砖都不动。这一条是我把整条链路从「听懂」一直走到「真去选图纸」才看见的，只看解析那一段是发现不了的。

这轮两件都修了。名字改成**从图纸本身长出来**：英文名按图纸编号自动拆词（`simple_wood_cabin` → "simple wood cabin"、"wood cabin"），两份图纸抢同一个尾巴（比如 "cabin"）就干脆都不认，免得先到先得；中文名跟着图纸走——本地那四份写进图纸文件自己的说明栏，程序生成的十份写在一张紧挨着名单的小表里，**不再写回她的听话逻辑**。万一两份图纸共用一个说法，她会把候选列出来问，而不是闷头挑第一个。档位那条改成：玩家点名要某份图纸、又没提大小，就按**那份图纸自己该在的档**算账（这个档是拿现成的预算尺子逐档实测出来的，不是我猜的）；玩家只要说了「大的」「精致的」「双层的」这类词，仍旧听玩家的。

结果（都是离线实测，不是估计）：一句话能盖出来的图纸**八份 → 十一份**；说了却什么也盖不出来的说法**八句 → 五句**；拿六十六句话逐句对照改前改后，只有五句变了，而且**正好就是修好的那五句**，老说法一句没变（三十八条老说法逐条钉进了测试）。

**有一件事我没有自作主张，交您拍板**：有四份图纸卡在门槛之间——比最小那档大（超一层或超八十块），又比第二档小（不够一百二十块），于是**哪一档都不收**，点名要它们就是「没有可用图纸」。别墅和城堡花园本来也一样，只因为它们在一张「按图纸原样盖、不按档位裁」的白名单里才能盖。改法有两种，都动到您定的门槛，所以我停下来问。**在您拍板之前，我让新名单故意不去认领这四份的中文说法**——认领了只会把现在的「盖错了」变成「盖不了」，那样更糟。

## 需要老板拍板的问题

### 问题 1：卡在门槛之间的那四份图纸，怎么放行？

- 背景：复杂度分五档，每档规定「最少多少块、最多几层」。最小那档限一层、最多八十块；第二档起码一百二十块。下面四份正好卡在中间，任何一档都不收，点名就报「没有可用图纸」：

  | 图纸 | 块数 | 层数 | 卡在哪 |
  |---|---|---|---|
  | 小房子（本地文件） | 26 | 2 | 层数超了最小档；块数不够第二档 |
  | 双层木屋 | 97 | 2 | 同上 |
  | 农舍 | 89 | 2 | 同上 |
  | 花园庄园 | 89 | 2 | 同上 |

  别墅（82 块）和城堡花园（90 块）情况一样，但它们在白名单里，所以能盖。
- 选项 A：把这四份也加进那张白名单（「按图纸原样盖」）。代价：一行改动；风险：低——白名单已有六项，行为是现成的。副作用：这四份从此不受档位裁剪，玩家说「建个小一点的农舍」也不会缩小。
- 选项 B：把第二档的最低块数从一百二十下调（比如到八十）。代价：影响所有走第二档的建造，可能让本该被拒的小东西也过关；风险：中。
- 选项 C：不动。代价：这四份永远只能靠说错名字（掉进默认的小房子）间接盖到，小屋轮不能用它们。
- 我的建议：**A**。它是现成机制的自然延伸，改动最小，而且和别墅/城堡已有的待遇一致；块数门槛是您定的整体标准，不该为四份图纸松动。

### 一、第 1 步读码结论

**1. 名字是怎么认的（已证实）** —— `ai/intent-parser.js` 里有**三条**路，不是一条：

| 路 | 位置 | 认什么 | 产出 |
|---|---|---|---|
| A 明确建造 | `parseDirectCommandIntent:281` → `parseExplicitBuildIntent:936` → `resolveBuildBlueprintName:992` | 有建造动词（build/建/造/盖/搭）+ 一条手写 if 链的关键词 | `params` 里**带 rawText 和完整 designSpec** |
| B 短语表 | `PHRASE_RULES:138-165`（`建个小屋` / `建个围墙` / `搭个箱子区` / `做个农田` 等固定短语） | 整句精确匹配 | `params` 里**只有 blueprintName**，无 rawText、无 designSpec |
| C 兜底 | `extractParams:1163` | BUILD 意图但没图纸名 | 围/箱子/农田各归一份，**其余一律 `small_house`** |

路 A 先于路 B 执行。任务书说的「只有四个名字」指的是路 B 那四条，实际上路 A 的 if 链已经覆盖十来个名字——**前提不成立，如实更正**。

**2. 图纸是怎么加载的（已证实）** —— `blueprint-loader` 只按文件名读 `blueprints/*.json`（现有四份）；`blueprint-selector` 把 `blueprintName` 当成**请求**而不是文件名，从社区索引 / 程序生成器 / 本地文件三处排候选，逐个过复杂度预算，第一个过关的胜出。所以「十份图纸」实际是程序生成的十份（`GENERATED_BLUEPRINT_NAMES`）+ 本地四份文件 = **十四份**。

**3. 档位是怎么定的（已证实）** —— `inferComplexityTier`：说了「展示级」→L5、「精致」→L4、「简单」→L2（带双层则 L3）、「应急」→L1、带双层→L3，**其余一律 L2**。预算表（`COMPLEXITY_TIER_SPECS`）关键三列：

| 档 | 块数区间 | 脚印 | 层 |
|---|---|---|---|
| L1 | 1–80 | 5×5 | 1 |
| L2 | **120**–250 | 7×7 | 1 |
| L3 | 250–500 | 9×9 | 2 |
| L4 | 500–1000 | 16×16 | 3 |
| L5 | 1000+ | 256×256 | 64 |
