## 一句话结论

门楼那盏吊灯笼盖不上，是因为她给「算路」定的时限是按走平路定的，而爬十格高的路要算好几倍的时间，所以每条路都在算到一半时被掐断、当成走不通；这一轮让她在全部候选都被掐断时，挑最有希望的几条再多算一会儿——真机上同样的高处目标改前算不出来、改后一次算通并把砖盖上了；顺带把「站在楼上、箱子在地面下不来」也修了，真机改前够不着、改后自己跳下去把东西放进了箱子。

## 白话摘要

她每次要爬到高处放砖，会先在脑子里「预演」几十条路线，每条只肯算一小会儿；这一小会儿是按走平地估的，平地够用。可门楼的灯笼离地十格，每条路都要先垫八到十一块脚手架再爬上去，算这种路要花平地的好几倍时间，于是三十四条路线全在算到三分之二处被掐断，她就报「找不到落脚点」，一步不动。我把门楼那次的现场原样在电脑上重放，证明那三十四条路只要给够时间条条能算通。

改法不是把每条路的时限都拉长（那样几十条候选一起算会把她卡死），而是：先照旧快速过一遍；只有当一条都没算通时，从被掐断的路里挑「已经算到离终点最近」的至多四条，每条再给四秒钟，而且算的时候每隔一小段就把手松开让她处理别的事，找到第一条通路就停。真机上搭了一座和门楼同样高、同样只能靠脚手架上去的靶子：改前八条路全部被掐断；改后同样八条先被掐断，随后补算的第一条一秒多就算通，她垫了十一块脚手架爬上去把砖盖好，而且从头盖一整栋小屋一次也没触发补算——矮目标没有被改坏。

顺带修的第二件事：她站在塔顶、箱子在地面六格之下，原来的自救只会在同一高度左右挪，永远下不去。现在她会先找台阶一级一级往下；实在没有台阶、而这一跳按她的血量扛得住时，就直接跳下去。真机上改前两次自救后报「够不着箱子」，改后一跳落地、打开箱子、把木头放了进去。

另外交给建造线一条实用的话：那盏灯笼那一步在存档里虽然标了「三次失败」，续建时**不用改任何存档**，她会从世界重新看一遍、那格还是空的就照常再试；这次拦她的是「同砖三败就停」的保姆规矩，不是存档。

## 需要老板拍板的问题

### 问题 1：「没台阶就直接跳下去」要不要保留
- 背景：箱子在楼下六格、周围没有任何台阶时，新逻辑会让她按血量算一笔账（跳下去掉的血不超过血量减三颗心，最多八格），扛得住就直接跳。这一跳在正常难度下会掉一点血（六格约一颗半心）。
- 选项 A：保留（默认）。代价：会主动掉一点血，但只在够不着箱子、且血量充裕时发生；日志里有一行明说「我跳了几格」。

- 我的建议：A。她本来就是「像玩家一样」的定位，玩家遇到这种情况也是跳下去；而且每次跳前都留了三颗心的余量，血不够会明确拒绝并写明原因。

### 二、第 1 步：预演怎么截断、`partial` 怎么判（读码 + 日志）

**2.1 分片机制（已证实）**。`actions/build.js` `previewControlledVerticalAccessPath`（改前 `:6089`）调 `bot.pathfinder.getPathFromTo(movements, bot.entity.position, goal, { timeout: 1000, tickTimeout: 40 })`——这是 mineflayer-pathfinder 的**生成器**（`index.js:70`），每 `next()` 跑一次 `AStar.compute()`（`lib/astar.js:67`）：一片最多 **40 ms** 就返回 `partial`（`:70`），总时长超 1000 ms 才返回 `timeout`（`:73`），开集空了才 `noPath`。`previewSlices` = 我们主动取了几片。片数上限 `controlledVerticalAccessPreviewSliceBudget`：

```text
maxSlices = min(16, max(6, 2 + ceil(直线距离 / 3)))        // 距离 = bot 到站位
```

门楼：她在 597.5,67,-22.5，站位 603,78,-5 直线 21.4 → 2 + 8 = **10 片**，与日志 `previewSlices=10` 逐字对上；远一点的站位 11–12 片。**10–16 片 × 40 ms = 400–640 ms，永远碰不到 1000 ms 的 `timeout`**——截断的是我们自己的片数上限，不是寻路器的时限。

**2.2 `partial` 时终点在哪、为什么全不算「可用部分终点」（已证实）**。`partial` 的 path 是到 A* 当前 `bestNode`（启发值最小的节点）的路。19 个生成候选的终点如 `603,75,-6`、`601,73,-2`、`607,71,-3`：离站位 2–7 格、离目标 4–7 格。判据 `isUsablePartialVerticalAccessEndpoint`（`:6127`）要同时满足：终点不与目标格相交；不低于 `minimumPlacementStandY`；**`isSafeStandPosition`——脚下现在就有整格实心**；到目标伸手 ≤ 4.5；能够到严格参照。这些终点全是半空中的脚手架柱位（脚下要等脚手架垫出来才实心）且离目标 > 4.5，两条都过不了；`endpointReachedGoal`（终点已在 GoalNear 范围内）也没有一个成立。所以 34 个全部落到 `rejection=preview_partial` → `noPath` 计数。

**2.3 候选生成（已证实）**。日志里两批不是「放宽多出 4 个」，是**两套不同来源**：
