## 白话摘要

上一轮我把她「放砖前先转身对准」这件事补齐了，但发现按下去那一刻，底层动作会替她再看一眼要贴的砖缝，把刚转好的身子扭回去。您拍板（决策 #58）把那处临时划给我，本轮就补了这六行：对中继器、比较器、活塞、粘性活塞、发射器、投掷器、侦测器这七种「朝向由人朝哪看决定」的方块，按下去时不再重看砖缝。

有两件事我特意去核了，没有想当然：

第一，**漏斗故意不走这条口子**。它的朝向本来就是「点了哪个面」决定的，那一眼正是它需要的，抢过来反而会坏事。天花和地板按钮也不会走到这里——它们更早就被另一条专用路径接走了，我读码确认了这条路走不到。

第二，**上一单修缮线加的「对着箱子、漏斗这类东西要先蹲下再放」不能丢**。不蹲下的话，右键会变成打开容器而不是放砖。新的放法把蹲下这一步照样包在外面，蹲下、放、起身，一个不少；老路上的蹲下行为也一点没动。

另外，失败时的表现我刻意保持原样：放没放上仍然由外面那层看方块来判断，用的还是它早就认识的那句「没变化」，没有给这一族方块多造出一种新的失败说法——不然日志和重试规则都要跟着改。

单测除了正面断言，还做了**反证**：把这六行关掉再跑，测试立刻变红。这样以后谁不小心删了它，测试会当场喊出来。

顺手查清了上一轮记下的一个小疑点：两份小屋图纸里各有「半张床」被算成朝向失控。查下来是**误报**——床是放脚那半时游戏自动生成头那半的，两半朝向天生一致，而施工顺序里脚也确实排在头前面，所以头那半根本不是单独放的。**程序不用改**，我只修正了自己那个离线核查工具的算法，让它别再误报。

离线回放：门楼一千二百多块的图纸上，四类计数（没人转身 / 转了白转 / 放完调不了档 / 永远对不上）**全是零**；别墅和本地十份图纸没有任何倒退；三张图纸的编号没变；六十组测试全绿。真机效果要等建造线第 20 轮收了这一单、再去续建门楼时才能看到。

### 一、第 1 步：那六行（提交 `f3ad00d9`）

落点：`actions/build.js` 的 `placeBlockAgainstReference()` 通用尾巴，紧挨床 / 站立旗帜头颅那两处专档之后、`bot.placeBlock()` 之前。

```js
const orientedLook = orientedPlacementLookDirection(blockName, placementStates(options))
const shouldSneak = shouldSneakForPlacementReference(reference) &&
  typeof bot?.setControlState === 'function'

if (orientedLook && typeof bot?._genericPlace === 'function') {
  context.logger?.log?.(`[BUILD_ORIENTED_PLACE_KEEP_YAW] target=… reference=… block=… facing=… source=… sneak=…`)
  if (shouldSneak) { bot.setControlState('sneak', true); await sleep(80) }
  try {
    await bot._genericPlace(reference, faceVector, { forceLook: 'ignore', swingArm: 'right' })
  } finally {
    if (shouldSneak) bot.setControlState('sneak', false)
  }
  await waitForPlacedBlock(context, target, blockName, options.orientedPlaceConfirmMs ?? 1200, 80)
  return
}
```

原尾巴的判断 `if (!shouldSneakForPlacementReference(reference) || typeof bot?.setControlState !== 'function')` 改写成 `if (!shouldSneak)`（德摩根等价，只是把同一个判断算一次），潜行分支本身一字未动。

#### 1. 哪些方块走这条口子（已证实）

判据是**生产函数** `orientedPlacementLookDirection()` 非空，不是另抄一份名单。实际落在这条口子上的只有七种：

`repeater`、`comparator`、`piston`、`sticky_piston`、`dispenser`、`dropper`、`observer`

**不走的，逐条给理由**：

| 方块 | 为什么不走 | 判定 |
|---|---|---|
| `hopper` | 语义表里是 `clickedFace:true`，`orientedPlacementLookDirection` 恒返回 null。它的 `facing` 就是被点的那个面，那一眼是它**需要**的，抢过来反而坏事 | 已证实（表 + 单测） |
| 地板 / 天花按钮、拉杆（`face≠wall`） | 表里有它们，但**它们到不了这里**：`placeBlock()` 的分发在 `tryPlaceStatefulBlock` 就把它们接走了，而且那条路失败时 `if (statefulBlock.error !== 'stateful_block_not_applicable') return statefulBlock` **直接返回、不落到通用路径** | 已证实（读码 `actions/build.js` 分发段） |
| 墙按钮 / 拉杆（`face=wall`） | `orientedPlacementLookDirection` 对 `face=wall` 返回 null（朝向由墙面定） | 已证实（单测） |
| 楼梯 / 门 / 栅栏门 / 熔炉族 / 活板门 | 各有自己的放置函数，早就传了 `forceLook:'ignore'` | 已证实（第 11 轮读码） |
| 床 / 站立旗帜头颅牌子 | 本函数里上面两处专档已处理 | 已证实 |

#### 2. `forceLook:'ignore'` 之后，视线由谁保证（第 1 步第 2 条，已证实）

从转身到发包这一段的完整调用链（通用路径 `placeBlock()` 内）：

```
equipBlockForPlacement()      → equipItemForPlacement() → bot.equip()      无 lookAt
orientBotForPlacement()       → lookTowardDirection() → bot.lookAt(...)    ← 视线在这里定下
placeBlockAgainstReference()  → [新档] setControlState('sneak') / sleep(80) 无 lookAt
                              → bot._genericPlace(..., forceLook:'ignore') 不再 lookAt
```

- `actions/build.js` 里全部 `lookAt` 只有 7 处：`5012` / `5025` 是 `lookTowardDirection` 自己；`1451`（土径 activateItem）、`4478/4496`、`4576`、`4834`（水桶 / 流体）都在流体与土径路径上，**与这七种方块无关**（已证实，逐处读过）
- **装备在转身之前**（`equip` 先、`orient` 后），所以换手不会打断视线（已证实，读码顺序）
- **潜行不改视线**：`setControlState('sneak', …)` 与那 80 ms 只发姿态包，不动 yaw/pitch（已证实：mineflayer 的 `setControlState` 走 `physics` 控制位，与 look 无关）
- **潜行与本档的先后**：潜行在外、放置在内，`try/finally` 保证异常也会起身（已证实，单测断言 `sneak=true` / `sneak=false` 成对出现）
- 仍存在的理论风险：`_genericPlace` 内部若因协议分支再 look（读过 `generic_place.js`，只有 `forceLook !== 'ignore'` 那一处）——**已排除**（已证实）

#### 3. 失败路径（第 1 步第 3 条，已证实）

| 走法 | 放置没成功时 | 调用方看到 | `isPlacementRetryableError` 认不认 |

### 三、第 3 步：半张床（查实为误报，程序不改）

- 事实 1：小屋图纸里床是两条 place 步——脚 `#103 (1,65,2) part=foot facing=south`、头 `#106 (1,65,3) part=head facing=south`，**脚排在头前面**（已证实，离线编译打印）
- 事实 2：香草规则里放脚那半时，头那半由游戏在 `脚 + facing` 方向自动生成，两半 `facing` 天生一致（本仓 `tryPlaceBedPairFallback` 的注释写着同一条规则）
- 事实 3：头那一步真正执行时，目标格已经是床了 → `repairObstructedTargetForPlacement` 走 `placementBlockNameMatches` + 闸门（床不在闸门名单里，返回空）→ 判 `placement_target_already_correct`，**这一步是空转**（已证实，读码）
- 结论：**不是真放歪，也不该加进 `utils/derived-placement-state-keys.js`**。头那半的 `facing` 是可比的、也确实正确；把它排除掉只会少一个正确的信号（床若真装反，脚那半照样会被抓出来）。**生产代码零改动**，我只修正了自己那个离线探针的分类（床 `part=head` 归为「派生」而不是「朝向失控」），两份小屋从各 1 变 0
- 遗留的理论风险（**合理推断**，未验证、优先级低）：若某次续建让头那一格**先**执行（例如只有头那格被破坏后的局部修复），`placementLookDirection` 对 `part=head` 返回 null，那次放置就会是随机朝向。现有 `tryPlaceBedPairFallback` 处理的是另一个方向的情况。已记在这里，未开卡片
