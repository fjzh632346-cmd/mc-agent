## 一句话结论

门楼上那批「放下去就没影」的方块，病根查实了：她挑来当依靠的那个邻居**根本点不动**（漏斗、中继器、红石线这类），已在编排施工顺序那一层修好并提交——拿门楼真图纸离线回放，会出这个毛病的地方从十三处（连锁算二十七处）降到**两处**，剩下这两处是图纸本身四周就只有点不动的东西、已被推到整个序列最末尾并留了日志；已完工的别墅和十份本地图纸的施工顺序**一个字都没变**，全部五十五组测试通过——真机效果要等建造线续建门楼时验证。

## 白话摘要

第一件事，先弄清「悬空放置」到底是什么。以前大家以为她放之前会检查「下面是不是空的」，其实**没有这道检查**：她是照常放一下，然后回头看一眼那一格——还是空的，就报这个错。所以真正的问题不是「悬空」，而是**她靠着放的那个邻居点不动**。有两类点不动：一类是右键下去会**打开界面或者改设置**的，比如漏斗、发射器、中继器、比较器——手里拿着方块去点它，只是把它的界面打开了，方块并没有放出去；另一类是**扁的**，比如红石线、铁轨，压根没有一个能点的整面。门楼上第十一轮炸的那三处，靠的正好是一个中继器、一个漏斗和一条红石线，三处三种，一个不落。

第二件事，修法。编排施工顺序那一层原来跟她犯同一个错——把这些点不动的东西也当成「有依靠」，于是就把方块排在了它们旁边。现在改成：轮到一块方块时，如果它周围**只有**点不动的东西，就先让它等着，等一个点得动的邻居排好了再轮到它；图纸里从头到尾都找不到点得动邻居的（门楼有两块），统一**推迟到整个序列的最末尾**并写一条日志，让她先把别的一千二百多块全盖完，而不是在半路把整个任务卡死。拿门楼真图纸离线回放：改前十三处会中招（按连锁算二十七处），改后只剩那两块，且都在末尾；已完工的别墅和十份本地图纸的施工顺序**逐字节不变**。配了十二组测试，另外把上一轮那趟「同向依靠」的保证也重新验了一遍，没有退步。

第三件事，如实说清剩下那两块。它们不是排序能救的——图纸就是那么长的，一块的下面是漏斗、旁边是比较器，另一块四周只有红石线。**要让她自己盖上这两块，得改她「放东西」的那段本事**：真人在游戏里遇到漏斗，会先按住蹲下再点，就放得上；她的程序里已经有这个「先蹲一下」的动作，只是名单里漏了漏斗、中继器这几样。这段本事归带游戏的那条线管，我这条线不碰，已经写成交接建议。

第四件事，顺带把「已有的补救机制为什么没救回来」也查实了：那套机制确实认得这个错、也确实触发了五次，但它补救的办法是**去把那个当依靠的邻居先摆出来**——摆出来的正是那个漏斗、那个比较器，等于把点不动的东西又摆了一遍，回头再放，当然还是放不上。

第五件事，本行的活：进度看板本身此前一直游离在版本管理之外，本轮整份收进了后勤线的分支，第四轮那支离线自测也正式挂进测试链成了一组，看板数据现在每次跑测试都会被检查一遍。看板补录了九处，现在八组七十条。另外提醒合并轮一句：主仓那份看板目录还没纳入版本管理，下次把总账推进来之前得先把它挪到备份目录，否则会像第十轮那样被挡住。

### 二、第 2 步：「悬空放置」（本轮主活，完成）

#### 2.1 口径：`unstable_air` 不是放置前检查（已证实，读码）

任务书假设它是「`actions/build.js` 放置前检查」。**不是**。三处抛出点全在**放置后确认**：

| 位置 | 上下文 |
|---|---|
| `actions/build.js:4141-4143` | `confirmPlacedBlock()`：放完 `bot.blockAt(target)`，不是目标方块时——非空气报 `place_failed:unstable:<name>`，**空气报 `place_failed:unstable_air`** |
| `actions/build.js:1796-1798` | 蜡烛叠放同款判定 |
| `actions/build.js:2323-2325` | 双层台阶同款判定 |

放置前的检查只有 `no_support_block`（`actions/build.js:191 / 903 / 910 / 914 / 1719`），语义是「**一个参照都找不到**」，与 `unstable_air` 是两回事。

所以「轮到它时会被判 `unstable_air`」的准确含义是：**运行时挑出来的参照候选全都点不动，点下去方块没出来**。「点不动」两类（游戏机制部分为**合理推断**，本线无真机；但项目代码自己已经为其中一部分编码了同一条规则，见下）：

- **A 类：右键被交互吃掉。** 真人放这类方块要先按住潜行。代码里确有这条：`shouldSneakForPlacementReference()`（`actions/build.js:4852`）会为 door / trapdoor / fence_gate / button / lever / `*chest` / `*anvil` / barrel / crafting_table / `*furnace` / bed 以及 `INTERACTIVE_REFERENCE_BLOCKS`（brewing_stand、enchanting_table、grindstone、lectern、note_block、jukebox、loom、stonecutter…）潜行。**名单里没有**：hopper、dropper、dispenser、crafter、repeater、comparator、daylight_detector、beacon、bell、cake、chiseled_bookshelf、decorated_pot、respawn_anchor、各色 shulker_box
- **B 类：没有可点的整面**（扁平/无碰撞）：redstone_wire、各种 rail、tripwire、lily_pad、snow

**关键佐证（已证实）**：第 11 轮真机三处炸点的参照物，正好全部落在这两类的**空档**里——中继器（A）、漏斗（A）、红石线（B）。项目自己的潜行名单差的就是这几样。

参照过滤器 `isPlacementReferenceBlock()`（`actions/build.js:5518`）与规划层 `isPlacementReferenceName()`（`utils/site-planner.js`）用的是**同一份** `NON_REFERENCE_BLOCK_PATTERNS`（运行时那份多 `^flower_pot$` / `^potted_` 两条），两边口径一致——**都不排除上面这些**。所以不是「规划层与运行时口径不一致」，而是**两层共用的那份口径与游戏实际不一致**。

**两趟的先后关系**（任务书要求写清）：轴向趟先跑、可点击趟后跑。后跑的这趟**只会推迟步**，而推迟可能把某个轴向步的同轴参照挪走——所以它的放行条件里**原样带上了第 6 轮的 `hasAxisReference()`**，从而不可能让第 6 轮的保证失效。这不是改第 6 轮的语义（`scheduleAxisReferenceSteps()` 一行没动），是新趟自己扛住旧不变量。**实测验证**：修后重跑第 6 轮探针，12 份图纸在普通与级联两种模式下轴向错序**全部 0**（已证实），并有单测钉住（用例 10）。

**为什么不做成「把不可点方块从 `NON_REFERENCE_BLOCK_PATTERNS` 里删掉」**：那份名单规划层与运行时共用，运行时删了就等于改放置分支（本轮红线不碰）；且删掉会让「一个参照都没有」的步数暴增，把大量步推进临时参照柱路径，风险面比排序大得多。

### 三、既有修复机制为什么没救回（任务书第 2 步第 5 条；已证实，读码 + 日志）

1. **触发是对的**：`isPlacementSupportFailure()`（`systems/building-system.js:5964`）明确包含 `place_failed:unstable_air`，所以 `BUILD_PLANNED_REFERENCE_REPAIR_TRIGGER` 5 次全部正常触发（证据包 §4）
2. **补救办法本身有病**：`ensurePlannedReferenceForStep()`（`:3160`）→ `findPlannedReferenceSteps()`（`:5782`）按「下(0) → 四侧(1) → 上(2)」找**图纸里计划要放的邻居**，过滤器是 `isPlannedPlacementReferenceBlockName()`（`:5817`）——它排除水/岩浆/火/地毯/床/牌子/旗帜/花草/树苗/梯子/火把/门/活板门等，**同样不排除 hopper / repeater / comparator / redstone_wire**。于是补救动作就是「把那个点不动的邻居先摆出来」：日志里 `reference=604,74,-2 referenceBlock=hopper`、`reference=604,75,-1 referenceBlock=comparator`、`reference=603,68,-10 referenceBlock=repeater`——摆完回头再放，参照还是点不动，**还是 `unstable_air`**

4. **不是死循环终态**：`isRetryableBuildError()`（`:8584`）的正则含 `place_failed` 与 `unstable`，所以这步是 `RETRYABLE_FAILED` 不是 `TERMINAL_FAILED`；但**任务**照样 fail，保姆脚本重发后续建对账把同一步又排第一，于是同点重复（#18/#21/#22）
5. **深度上限 2**（`plannedReferenceRepairDepth >= 2`）没被触到，不是原因
