## 2. 关键结论

1. **已证实** 三次都是服务器主动判定 `lost connection: Timed out`（keep-alive 应答超时）；客户端在此之前没有任何错误、警告或崩溃。
2. **已证实** 断线前 bot 进程并没有"整体卡死"：忙碌段落里每 0.3–2.5 s 就有一行日志（相邻两行最大间隔 2.38 s / 2.46 s / 1.09 s），但每 10 s 一次的 `[状态]` 定时器（`bot.js:982` `setInterval(..., 10000)`）连续漏拍 24.8 s / 41.5 s / 37.4 s。定时器和 socket 读取同属事件循环的宏任务阶段，它们一起被饿死了。
3. **已证实** 三次断线前的忙碌段落（见 §6 表）：第 1 次是 `BUILD_VERTICAL_ACCESS_CANDIDATE` 预览 48 条（13 s）；第 2、3 次是 `utility-search`（找合成台）49 / 39 条 + `auto-prep` / `STAGING_CRAFT_*` 循环（41 s / 30 s）。两条路都在同步 API 上打转：`bot.findBlocks({ maxDistance: 32/64, count: 32/64 })`（`systems/UtilityBlockSearch.js:207-215`，每次暂存合成尝试调 3 次）与 `bot.pathfinder.getPathTo(...)` / `getPathFromTo`（`actions/build.js:6389`、`6049`、`6060-6076`）。
4. **合理推断** 根因链：忙碌段落超过 15 s 不回到事件循环的 I/O 阶段 → 服务器发来的 `keep_alive` 留在 socket 缓冲区没被读 → `minecraft-protocol` 的应答（`node_modules/minecraft-protocol/src/client/keepalive.js:9-24`，收到才回）发不出 → 服务器 15 s 没等到应答判 Timed out 并关连接 → 忙碌段落一结束客户端立刻读到踢出包 / ECONNRESET。第 1 次的时间戳把这条链钉死了：41 候选预览结束 16:36:19.814，踢出包 16:36:19.972，相差 158 ms。第 3 次是写包时才撞上 ECONNABORTED（服务器 4 s 前已关连接）。
5. **已证实** 无自动重连：`bot.js:1602-1608` 的 `bot.on('end')` 只清定时器、停 TickLoop 与 TaskManager；进程继续活着 17.8 / 11.4 / 10.4 分钟直到人工杀掉（只杀本仓 bot.js 进程）。
6. **已证实** 假死后的误导信号：`[状态]` 每 10 s 继续打印缓存位置（三段断线后分别 107 / 68 / 63 行）；第 2、3 段里箱子交互的 promise 链仍在本地空转：`CHEST_OPEN_ATTEMPT` → 20 s `windowOpen` 超时 `CHEST_OPEN_FAILED` → `CHEST_PATH_ESCAPE_ATTEMPT` ×3 → `CHEST_PATH_UNREACHABLE` → `STAGING_CRAFT_DEPOSIT_FAILED`，每 65 s 一轮（第 3 段断线后 CHEST_OPEN_FAILED 9 次、CHEST_PATH_UNREACHABLE 9 次）。**注意：三段日志里所有 CHEST_OPEN_FAILED 都发生在断线之后**（第 1、2 段为 0 次），它不是箱子 bug，是假死的症状。
7. **已证实** 假死后仍在写存档：run 的 `reconciliation.at = 2026-09-01T17:40:09.325Z`、`updatedAt = 17:40:10.416Z`（第 3 次断线后 10 分钟），verified=998 / pending=828 / stateRepair=37。**合理推断** 这次 reconcile 读的是断线前缓存的区块，可信度存疑；`status = BLOCKED_MATERIAL_SHORTAGE` 同样是假死进程的本地误报（第 11 轮反馈已说明）。
8. **UNKNOWN** 具体是哪一层不让路：是同步扫描本身连续占用，还是 `await` 链只在 microtask 里续接、从不回到宏任务？需要修缮线用 `node --cpu-prof` 或在 keepalive 处加日志复现确认。
9. **合理推断** 服务器侧判定窗口约 15 s（原版 keep-alive 逻辑），所以任何 >15 s 不读 socket 的忙碌段落都会掉线；第 11 轮观察到的"约每 30 分钟一次"只是这类段落出现的频率，不是周期性机制。

'use strict'

module.exports = function (client, options) {
  const keepAlive = options.keepAlive == null ? true : options.keepAlive
  if (!keepAlive) return

  const checkTimeoutInterval = options.checkTimeoutInterval || 30 * 1000

  client.on('keep_alive', onKeepAlive)

  let timeout = null

  client.on('end', () => clearTimeout(timeout))

  function onKeepAlive (packet) {
    if (timeout) { clearTimeout(timeout) }
    timeout = setTimeout(() => {
      client.emit('error', new Error(`client timed out after ${checkTimeoutInterval} milliseconds`))
      client.end('keepAliveError')
    }, checkTimeoutInterval)
    client.write('keep_alive', {
      keepAliveId: packet.keepAliveId
    })
  }
}

function previewControlledVerticalAccessPath(bot, movements, goal, timeoutMs, options = {}) {
  const pathfinder = bot?.pathfinder
  const fallback = () => ({
    ...pathfinder.getPathTo(movements, goal, timeoutMs),
    previewSlices: 1
  })
  if (typeof pathfinder?.getPathFromTo !== 'function') return fallback()

  const maxSlices = controlledVerticalAccessPreviewSliceBudget(bot, goal, options)
  const requestedTickTimeoutMs = Number(options.verticalAccessPreviewTickTimeoutMs ?? 40)
  const tickTimeoutMs = Number.isFinite(requestedTickTimeoutMs)
    ? Math.max(5, Math.min(timeoutMs, requestedTickTimeoutMs))
    : Math.min(timeoutMs, 40)
  const generator = pathfinder.getPathFromTo(
    movements,
    bot.entity.position,
    goal,
    {
      timeout: timeoutMs,
      tickTimeout: tickTimeoutMs
    }
  )
  let preview = null
  let previewSlices = 0
  while (previewSlices < maxSlices) {
    const next = generator.next()
    if (next.done) break
    preview = next.value?.result || next.value || null
    previewSlices += 1
    if (preview?.status !== 'partial') break
  }
